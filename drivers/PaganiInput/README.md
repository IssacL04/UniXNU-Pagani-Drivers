# PaganiInput

Physical input for the OnePlus 13T PKX110, using the original 21H461 `IOHIDDevice` parser and event dispatch. `pagani-buttons=1` starts the PMIC keys; `pagani-touch=1` starts a separate S3910 device with Digitizer/Touch Screen as its primary usage. A personality scoped to product `Pagani S3910`, SPI and usage 13/4 matches the original `IOHIDEventDriver`. The button descriptor remains separate. Stage7Probe starts them after the original HID resources and the GOP display are available. Their failures are reported without failing display startup.

The S3910 path adopts QUP1 S4, configures the board pins, resets the controller, disables HBP raw reports and selects the vendor's on-controller LBP mode. Reads use full-duplex SPI with `0xff` transmit bytes. The first validated header selects TouchComm v1 or v2. V2 checks header CRC6 and payload CRC16, uses ACK/RETRY for continuation, retains the sequence bit when a command is retried, and respects the controller read/write limits. It installs and reads back a bounded report format before accepting contacts. Ten stable contact IDs map to 0..32767 coordinates; finger and glove classifications are accepted, palms are dropped, and removed contacts receive explicit release reports. A transport failure releases held contacts and disables that device until reboot. No controller firmware is uploaded or erased.

The PMIC observer reads PON SID 0 peripheral 0x13 and GPIO SID 1 peripheral 0x8d. On this board PON bit 7 is Power, PON bit 6 is Volume Up, and the active-low GPIO is Volume Down. The driver never writes PMIC peripheral configuration. Keys are polled every 8 ms and debounced per key on both edges: the PON keys, whose RT_STS the PMIC already debounces, need 16 ms of a stable level and are not pressed again within 32 ms of their release (the pmk8350-class software debounce of Linux pm8941-pwrkey); Volume Down and the Plus key use Android's 32 ms gpio-keys interval. A failed SPMI read releases Power and both volume keys at once and restarts their debounce. Report 2 holds one bit per key, so keys confirmed in the same poll (the Power + Volume Up screenshot chord) arrive in one report; held keys are reported once, because 21H461 SpringBoard repeats volume itself (`-[SBVolumeControl increaseVolume]`, 0.333 s then 0.042 s) and times long and multiple presses.

The Plus key on the left side is TLMM GPIO 97 (Android `oplus_magic_buttom`, active low, external pull-up). At start the driver applies Android's pin state (gpio function, no pull, input, 6 mA), checks it by readback and restores the original CFG at cleanup; without the pin the other keys still start. The key is not reported itself: it drives the iPhone ring/silent switch, the Telephony Ring Select element (0x0b/0x2e) in bit 4 of report 2, 1 = ring and 0 = silent. Each confirmed press flips it. It starts at ring and is armed by a confirmed release, so a key held or a line stuck low since boot cannot silence the phone. The first poll reports ring, before backboardd's `BKButtonHIDEventProcessor` copies the switch level from IOHIDEventDriver's element (`copyEvent` keyboard 0x0b/0x2e); later changes reach `-[SpringBoard _handleRingerSwitchEvent:]` (silent when the level is 0). SpringBoard acts on them only when MobileGestalt `ringer-switch` is true, which libMobileGestalt derives from a `function-button_ringerab` property in `IODeviceTree:/buttons` (any value; AppleM68Buttons, the only parser of its value, is not prelinked). The switch level is not persistent: every boot starts at ring.

Board addresses and wiring are supplied by the device's `PaganiPeripherals.h`. SM8750 clock, RPMh and SPMI operations come from `Sm8750Platform/PeripheralIO.h`. SPI uses the selected `QcomGeniSpi` component. The main `build-pagani-peripherals.py` qualifies the original 207-slot HID ABI and the compiled subclass; `build-stage7-display.py` includes the late-registered objects in its archive.

Run `python3 <device>/scripts/test-peripherals.py --tree <resolved-tree>` for the portable transport, contact, debounce and MMIO tests. The tests use simulated hardware. The HID descriptor layout follows [NativeHidInput](https://github.com/UniXNU/NativeHidInput/tree/5f3a37c), with its notice retained in `LICENSE.HID`.

`pagani-peripheral-status=1` keeps diagnostic rows below the camera cutout, refreshed after frame copies and once per second. `KEYS`, `TOUCH` and `PANEL` show the current stage, hexadecimal result `r`, hexadecimal sample `v`, and decimal successful-report/command count `n`. Setup failures retain the failing stage. For keys, `PMIC sample` packs PON in bits 8..15, GPIO in bits 0..7, the Plus key input level in bit 16 (1 released), the switch in bit 17 (1 ring) and Plus key availability in bit 18 (0 when TLMM GPIO 97 did not read back its configuration; the switch then stays at ring), and a row left at `Plus key` points at the TLMM access itself; for touch, `ATTN wait` shows the pin level, `HID report` shows the active contact-ID mask, and TouchComm failures show `T<version> <command> <stage>`. Version 0 means that no valid protocol header has been identified. After a successful SPI read, `header` and `continued` store the first four bytes in `v` in little-endian order; if the transfer itself fails, `v=0` means no header was recorded. Validation stages retain the rejected length, status or value. `r=0` from HID means the kernel accepted a report; it does not prove that backboardd received it. Disable the overlay after input qualification to uncover the top of the UI.

An SPI transport failure adds two rows: `SPI fw=... if=... st=... irq=...` and `SPI FIFO tx=... rx=...`, all hexadecimal. `fw` and `if` are the firmware revision and interface-disable register captured at initialization. `st`, `irq`, `tx` and `rx` are the GENI state, master interrupt status and FIFO status saved by the transport before cancellation. DMA failures replace the second row with `SPI DMA tx=... rx=... ti=... ri=...`: DMA interrupt snapshots and the TX/RX length-in counters. The existing library may have acknowledged error bits before taking this snapshot, so a zero IRQ value alone does not exclude a DMA fault. SMMU setup failures instead show the selected slot/bank and conflicting SMR/S2CR registers. The adapter forwards saved values instead of rereading registers after recovery.

The first successful SPI read also retains two rows: `SPI RX n=... h=... a=.../... rst=...` and `SPI dma=... ti=... ri=... st=... dly=...`. All values are hexadecimal: `n` is the requested length, `h` packs up to four RX bytes in little-endian order, `a` samples ATTN before/after the transfer, and `rst` is the RESET GPIO IN_OUT register's low two bits (input bit 0, output latch bit 1). The second row records the DMA selection, the library's TX/RX length-in readings and GENI state and the delay-counter register after the call returns. PIO does not supply DMA counts. These rows survive a later protocol-header rejection; a later transport error replaces them with its pre-cancel snapshot.

Build 50 reached the lock screen after skipping Setup. The user confirmed short power-key presses switch the screen off/on and a long press opens the shutdown UI; the key report count also changes for volume presses. Touch stopped at `TouchComm start` with `r=ffffffb9` and no reports. Build 51 passed the full build but still had no touch response: `TOUCH T0 00 header r=ffffff92 v=0 n=0`. This is a timeout in the first four-byte SPI transfer, before protocol identification. No register snapshot was visible in that image, so FIFO availability and completion status remain unresolved.

Build 53 reported the same first-transfer timeout with `fw=102 if=1 st=41 irq=0` and empty FIFO status. `if=1` confirms that the FIFO interface is disabled. The current candidate selects the existing SE DMA implementation when that flag is set. It allocates separate 4 KiB cached TX/RX pages, performs explicit cache maintenance and plans an exclusive VA64 SMMU bypass for the board's QUP stream `0xa3`. The planner preserves the UFS bank and refuses existing translated, shared, masked or duplicate QUP mappings, including firmware bank 0. Such a refusal stops before publishing DMA addresses and exposes the mapping for diagnosis. No global SMMU fault policy is changed.

Build 54 reached `TOUCH T0 00 header r=ffffffb9 v=0 n=0` without either transport-error row. The SPI call returned success, then TouchComm rejected a four-byte zero header with `-71`. Touch setup exited before `IOHIDDevice::start`; this does not establish valid sensor data or a working HID event path. The first-success snapshot above addresses this diagnostic gap without changing transport mode, reset timing or protocol acceptance.

The current candidate explicitly requests the two board-defined touch rails before reset. It resolves `ldob4`/`ldob16` from command DB, verifies the addresses captured on the 13T, then requests 1800/3100 mV in high-power mode and waits 200 ms after both acknowledgements. Unknown resources, occupied TCSes, write-readback failures or missing acknowledgements stop startup. Power failures retain `PWR a=... hw=... t=...` and `PWR st=... c=.../.../...` in the existing two diagnostic rows. Successful requests establish controller acknowledgement, not a physical voltage measurement. Cleanup leaves shared rail votes enabled.

The SPI CS/word delay counters are explicitly set to the captured OnePlus values 50/0 (`0xc800`) and checked before reset. `dly` preserves the actual register at the first successful read. The changes follow the 13T Android capture and the [hummer S3910 power diagnosis](https://github.com/2426120557/UniXNU-hummer/blob/55e5c82772e047a776d17a975b9c9cac86f04fe5/GSI-PORT-PLAN.md), with the 13T's own resource names, voltages and SMMU policy. The existing SE DMA and TouchComm validation remain in use.

Build 56 subsequently returned `a5 10 1c 00`, reached `HID report r=0`, and showed a nonzero contact mask while pressed and zero after release. Swipes and a power-menu Cancel tap did not respond. The former keyboard-first identity and lack of downstream observation left kernel report acceptance indistinguishable from UI delivery. The new touchscreen personality and descriptor address that identity gap; they still need hardware validation.

Touch reports now wait for the attached event driver, usage 13/4, Built-In/DisplayIntegrated and actual digitizer collection dispatch. Before replacing this instance's dispatch entry, the build qualifies the exact 220-slot driver table, 37-slot event table and required field/method boundaries in the pinned original image. Runtime table identity is checked again. Other drivers and original executable bytes are unchanged. Edge-origin contacts retain `0x800` through movement and lift, following the guide's pinned ShengHidInput reference. The initial border is 48 framebuffer pixels, normalized using the actual console geometry; physical calibration remains pending. The owned dispatch table lives until reboot.

After a parsed frame, the two SPI rows become `HID b=... use=.../... ev=.../... e=...` and `XY in=.../... out=.../... mask=...`. Binding bits are 1 driver found, 2 qualified table, 4 usage 13/4, 8 integration/collection properties, and 16 dispatch installed (`b=1f` when complete). `ev` counts dispatch calls/digitizer collections; `e` counts contacts beginning at an edge. Counts are decimal; the other fields are hexadecimal. `in` is the first active contact in 0..0x7fff descriptor space, `out` is the first active digitizer child in 0..0x10000 IOFixed space; both retain the last active coordinates after release. `mask` is the last collection event mask. `HID wait` or `HID bind` stops successful-report counting until binding is qualified. Protocol/transport failures retain their own diagnostic rows. A dispatch count still does not prove backboardd or UI acceptance.

The two touch rail requests share the apps RSC DRV-2 with the A830 GPU driver's host votes. Both drivers take the weak, linker-merged word `sm8750_rpmh_drv2_owner` first (`Drv2Lock.h`: atomic 0-to-owner swap, 10 us waits, at most 2 s; the touch owner is `TUCH`, the GPU's `A830`). If the word stays owned for 2 s, touch setup stops at `power lock` with `r=fffffff0` and `v` holding the waits, before any TCS register is written. At boot the two never contend (the GPU starts after the peripherals); the lock covers the GPU's run-time DDR floor changes. `pagani_input_touch_events` (weak, also defined by the GPU driver) counts parsed touch frames; the GPU DCVS reads it for the touch boost and the slumber pre-wake. `pagani_input_key_events` (weak, also defined by PaganiArmCpu) counts key reports the HID parser accepted (a press, a release, a ring/silent change); PaganiArmCpu's screen-off policy (`pagani-screenoff` bit 0) reads it, a key on the dark display lifting the CPU's screen-off levels. `Test/peripherals.cpp` checks that only accepted reports count. `pagani_input_power_held` (weak, also defined by BootProgress `UfsLog.c`) is 1 while the debounced physical Power key is down, a script's key not counting: a long press ends in the PMIC's reset, so the UFS log stays off the wire meanwhile. A failed PMIC read leaves it as it was: only a confirmed level changes it.

Current limits: ATTN and keys are sampled every 8 ms; GIC interrupts and system-sleep wake are not implemented. SE status generation remains enabled for DMA polling while ArmCpu leaves the unused SPI interrupt masked. SPI uses retained GENI microcode; build 56 demonstrated valid protocol and contact frames through SE DMA. Once exposed to the engine, the 8 KiB allocation is retained until reboot because reset completion is not yet qualified. Reaching HID submission implies that checked RPMh requests completed, but physical rail voltage was not measured. GPI DMA, v1 command fragmentation, firmware recovery and HID hot-unplug are not implemented. The firmware must expose LBP and an application identification report. Real contact orientation, report continuity, UI delivery and system edge gestures still need device validation. Host tests do not establish usable touchscreen input.

The transport was compared with the [OnePlus S3910 HBP implementation](https://github.com/OnePlusOSS/android_kernel_modules_and_devicetree_oneplus_sm8750/tree/6a196f79f77acd55cf302e1696c038e4cad99254/vendor/oplus/kernel/tp/hbp/hbp/chips/synaptics/s3910) and [data-a-live's S3910P path](https://github.com/ShueiTsuki/data-a-live/blob/ba094818ed915cd3689937180a6f619c0e9c86ef/wsl/pandora_touch.c). The latter also identifies v1/v2 and fills reads with `0xff`; its SM8850 GPI, regulator wiring and Xiaomi raw-frame algorithm are board-specific. The local protocol implementation remains independent of the Linux driver. Tests exercise the actual SPI read adapter, fixed v2 command bytes, independent CRC checks, fragmented reads/writes, delayed/retried replies, corrupt packets and bounded raw-frame draining.

## Input script (scripted self-test)

`pagani-input-script=<mask>` lets the phone drive its own touch screen and keys for a test run nobody attends: bit 0 types on the keyboard in Spotlight, bit 1 presses the volume keys, bit 2 opens Control Center (`7` runs all three in that order, 5 s apart). `pagani-input-script-at=<s>` starts it that many seconds after the touch driver's start (default 240; its own lines then print the deadline in mach absolute time, the clock of the `kbt` lines of `phone-keyboard-trace.patch`, which on this board runs from the SoC reset, about a minute ahead of the boot log). With the mask 0 or absent nothing changes: no state, no line, no extra timer, the key poll passes its report unchanged. Unknown bits alone (`off, mask 8`) or a console other than 1216x2640 (`off, screen WxH`) log one line and stay off.

The touch device runs the timeline from its existing 8 ms timer (`InputScript.h`, integer arithmetic, no sleeping on the HID path). Its synthetic finger is contact 9 (the controller numbers real contacts from 0) and takes the real contacts' report builder and send: a down frame, the same frame every 16 ms while a tap holds still, a move frame every timer tick (8 ms) along a swipe, and a final frame with the tip off at the last position. The descriptor has no in-range usage, so the contact's presence plus Tip Switch carries the in-range transitions exactly as for a real finger; swipes that start inside the 48-pixel band get the edge-origin mark (`0x800`) through `pagani_touch_edge` like real ones. Script frames count in `pagani_input_touch_events` and script keys in `pagani_input_key_events`, so the CPU and GPU see them as input. Keys go to the key device through one shared word: its poll adds the held bits to the debounced report 2 until the planned release plus 40 ms, so a key cannot stay down if the touch device stops; the script never touches the ring/silent bit.

Sequence (coordinates in framebuffer pixels, 405.333x880 points at @3x): every script starts with `wake` (Power for 120 ms only while PaganiPanel's `pagani_screen_state` reads the display off, then up to 3 s for it to come on) and `home` (Consumer Menu, report 2 bit 0, 120 ms); the first script also swipes the home gesture (`unlock`, 608,2628 to 608,1748 in 250 ms: SpringBoard's own PPT home swipe, bottom centre up a third of the screen) and presses Home again. On 21H461 with `home-button-type = 2` SpringBoard treats that press as an emulated home button (`-[SBHomeHardwareButton emulateHomeButtonEventsIfNeeded:]`): on a dark locked screen the press only wakes it (`unlockUIFromSource:15` with TurnOnScreenFirst; the release is "ignored because we don't unlock on button up"), on the lit lock screen it unlocks (no passcode), on the home screen it is an ordinary home press; the bottom swipe unlocks a lit lock screen and is harmless on the home screen, so either path alone still ends on the home screen. Bit 0: `spotlight` (608,1320 down to 608,1770 in 250 ms, the home screen's pull-down, outside every edge band), 3 s for the keyboard, then taps of 80 ms with 600 ms between on the `iPhone-PortraitChoco405` keyboard (keyplane at y 589 pt above the 75-pt dock): `shift` 78,2181, `a` 121,2019 three times, `123` 78,2343, `abc` 78,2343, `globe` 128,2495 (the dock's left item at 460 ppi), then `close` (the home gesture again) and `home`. Bit 1: `up 1..3` (Volume Up) and `down 1..3` (Volume Down), 120 ms presses with 800 ms between. Bit 2: `open` (1064,12 down to 1064,1200 in 300 ms: inside the top band, in the right quarter SpringBoard gives Control Center on a phone and right of the island at x 420..796), 3 s, `close` and `home`. All three take about 45 s.

The run ends at once, finger lifted and keys released first, when a real object appears on the screen (any classification the controller reports, palms included; `s3910_objects`), a real key is pressed or the ring/silent switch moves, the controller stops, a report is refused, or the driver stops; at the start time it also needs the qualified HID binding and no finger already down. While it runs, a real report without objects is held back when the synthetic finger is down, since it would lift it.

Ramoops U lines, one per step: `input script: armed 7 at 240s` (driver start), `input script: start 7 at 240000ms keys on` (`keys off`: no key device polling), `input script: kb wake on` (or `kb wake power, on 412ms`, `kb wake power, off 3000ms`, `kb wake off, no keys`), `input script: kb home` (`, no keys` when skipped), `input script: kb unlock 608,2628>608,1748 250ms`, `input script: kb tap a 121,2019`, `input script: vol up 1`, `input script: cc open 1064,12>1064,1200 300ms`, then `input script: done 7 in 44296ms`, or `input script: abort kb tap a: real touch` (also `real key`, `touch stopped`, `HID report refused`, `driver stopped`, and at the start `abort: touch HID not ready b=<binding bits>`). A full run logs 30 short lines, about 2 KB of the 32 KiB events ring. `Test/InputScriptTests.h` (run by `test-peripherals.py`) checks the program, every frame time and coordinate, the report bytes, the keyboard keys against the layout's frames, the edge bands, the key device side through the real `pollButtons`, the wake wait, every abort path and the default-off path.
